📌 ORACLE MULTITENANT — COMANDOS + PONTOS QUE A PROVA AMA
===============================================================================

✅ 1) CRIAÇÃO E CONTROLE DE PDB (COMANDOS ESSENCIAIS)
-------------------------------------------------------------------------------

🧱 Criar PDB (a partir do PDB$SEED)
----------------------------------
CREATE PLUGGABLE DATABASE pdb1
  ADMIN USER admin IDENTIFIED BY "<SENHA_ORACLE>"
  FILE_NAME_CONVERT = ('/pdbseed/', '/pdb1/');

🔓 Abrir PDB
------------
ALTER PLUGGABLE DATABASE pdb1 OPEN;

💾 Salvar estado (AUTO OPEN após restart)
----------------------------------------
ALTER PLUGGABLE DATABASE pdb1 SAVE STATE;

🔁 Comandos rápidos (abrir/fechar/todos)
---------------------------------------
ALTER PLUGGABLE DATABASE pdb1 OPEN;
ALTER PLUGGABLE DATABASE pdb1 CLOSE IMMEDIATE;
ALTER PLUGGABLE DATABASE ALL OPEN;

===============================================================================
2) 2️⃣ COMPONENTES QUE A ORACLE AMA COBRAR
===============================================================================

📦 2.1 Containers (conceito que cai MUITO)
-------------------------------------------------------------------------------
| Container   | Função            | Observação de prova                      |
|----------- |------------------- |------------------------------------------|
| CDB$ROOT   | Metadados comuns   | Onde ficam usuários comuns               |
| PDB$SEED   | Template           | Read Only, nunca altere                  |
| PDB        | Banco isolado      | Pode ser aberto/fechado individualmente  |


🔐 2.2 Usuários comuns x locais (CAI!)
-------------------------------------------------------------------------------

👤 Common User (Usuário Comum)
- Criado no ROOT
- Prefixo obrigatório: C##
- Existe em todos os PDBs

Exemplo:
  CREATE USER C##MONITOR IDENTIFIED BY Oracle_123 CONTAINER=ALL;

👤 Local User (Usuário Local)
- Criado dentro do PDB
- Existe só naquele PDB

Exemplo:
  CREATE USER app_user IDENTIFIED BY Oracle_123;


📌 Pergunta típica:
"Qual usuário pode administrar todos os PDBs?"
✅ Resposta: Common User


🧠 Mnemonic da multitenant (decora!)
-------------------------------------------------------------------------------
• CDB  = casa
• ROOT = regras
• SEED = molde
• PDB  = morador


===============================================================================
🏗️ 2.4 Application PDB (nível prova)
===============================================================================

😈 A Oracle ama isso.

✅ O que é?
- Modelo para padronizar aplicações

✅ Permite:
- Patching centralizado
- Upgrade coordenado
- Menos downtime

🧩 Componentes:
- Application Root
- Application PDB
- Application Seed (opcional)

📌 Conceito-chave:
Você aplica o patch UMA vez no Application Root
→ e ele propaga para todos os Application PDBs


===============================================================================
⚠️ 2.5 Onde executar comandos (PEGADINHA #1)
===============================================================================

| Ação                  | Onde executar |
|----------------------|---------------|
| Criar Common User     | ROOT          |
| Criar Local User      | PDB           |
| Criar PDB             | ROOT          |
| Abrir/Fechar PDB      | ROOT          |
| Criar objetos da app  | PDB           |


===============================================================================
🚚 2.6 Upgrade e transporte de PDB (conceito)
===============================================================================

✅ A prova cobra conceito, não script longo.

✔️ PDB pode ser:
- Plugado / desplugado
- Upgradado isoladamente
- Transportado entre CDBs compatíveis

📌 Regras importantes:
- Versão de destino ≥ versão de origem
- Compatibilidade de charset
- PDB$SEED nunca é transportado

===============================================================================
2️⃣ APPLICATION PDB — PROFUNDIDADE (NÍVEL DIFÍCIL)
===============================================================================

⚠️ Aqui é onde muita gente cai.

🎯 O que a prova quer MESMO
-------------------------------------------------------------------------------
❌ Não é sintaxe
✅ É entender o ciclo de vida da aplicação

-------------------------------------------------------------------------------
🏗️ Arquitetura correta
-------------------------------------------------------------------------------
CDB
 └── Application Root
      ├── Application Seed (opcional)
      └── Application PDBs

📌 Regra de ouro
-------------------------------------------------------------------------------
✅ Objetos da aplicação vivem no **Application Root**
✅ Dados vivem nos **Application PDBs**

-------------------------------------------------------------------------------
🔁 Ciclo de vida da aplicação (CAI!)
-------------------------------------------------------------------------------
1️⃣ Criar Application Root
2️⃣ Instalar aplicação (BEGIN INSTALL)
3️⃣ Criar Application PDBs
4️⃣ Finalizar versão (END INSTALL)

Exemplo conceitual:
  ALTER PLUGGABLE DATABASE APPLICATION app_sales BEGIN INSTALL '1.0';

Depois:
  ALTER PLUGGABLE DATABASE APPLICATION app_sales END INSTALL;

🎯 Pegadinha
-------------------------------------------------------------------------------
⚠️ Sem `END INSTALL`, a versão **NÃO é registrada**

-------------------------------------------------------------------------------
🩹 Patch e upgrade de Application
-------------------------------------------------------------------------------
✅ Patch aplicado no **Application Root**
✅ Propagado automaticamente
✅ Application PDBs entram em:
   - `APPLICATION PATCH`
   - `APPLICATION SYNC`

📌 Pergunta clássica:
Onde aplicar o patch?
👉 **Application Root**

-------------------------------------------------------------------------------
🚫 Erros comuns de prova
-------------------------------------------------------------------------------
❌ Criar tabelas da aplicação direto no Application PDB
❌ Aplicar patch em cada PDB
❌ Confundir Application Root com CDB$ROOT

-------------------------------------------------------------------------------

3️⃣ UPGRADE + TRANSPORT PDB (CENÁRIOS REAIS)
===============================================================================

🏢 Aqui a Oracle simula ambiente corporativo.

-------------------------------------------------------------------------------
⬆️ Upgrade de PDB (isolado)
-------------------------------------------------------------------------------
✔️ Um PDB pode ser:
- Plugado em um CDB mais novo
- Upgradado sem parar outros PDBs

Fluxo conceitual:
1) Unplug PDB
2) Plug no novo CDB
3) Upgrade do PDB

📌 Regra:
✅ Versão do CDB destino ≥ versão do PDB

-------------------------------------------------------------------------------
🚚 Transport PDB (CAI!)
-------------------------------------------------------------------------------
Pode transportar:
- Dados
- Metadados
- Entre hosts diferentes

⚠️ Restrições cobradas:
- Charset compatível
- Endianness compatível (ou conversão)
- Mesmo `COMPATIBLE`
